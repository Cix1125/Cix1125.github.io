# 案例 01 · 小微商户进销存系统

**角色**：独立完成（调研 → 建模 → 开发 → 交付 → 迭代）
**时间**：2026.09 —【待填：交付周期】
**技术**：低代码建表思路 + 单页应用（原生 HTML/CSS/JS，无框架依赖）
**可验证材料**：`demo/inventory.html`（可交互 Demo，离线可跑）

## 一、问题（我去现场看到的）

**我舅舅开的一家小店**（零售）
我在店里待了一天，看到的是：

- 进货、卖货、退货都记在一个本子上，月底靠计算器对账
- 经常出现「本子上有、货架上没有」或反过来
- 老板**完全不知道哪件货快没了**，往往是客人问了才发现没货
- 一批货赚了多少、压了多少钱，说不清

**老板的原话是**：
> 【待填：把他/她最有代表性的一句话原样记下来，这句比任何分析都值钱】

---

## 二、我做了什么

### 1. 先画流程，不写代码
把业务拆成四个动作：**进（入库）/ 出（出库）/ 存（库存）/ 单（订单）**，画成一张流程图给老板看，确认「是不是这么回事」。他发现我把「退货」漏了 —— 这一步如果不做，后面全白搭。

### 2. 建三张表（数据建模）
| 表 | 存什么 | 关键设计 |
|---|---|---|
| 商品表 | 名称、货号、单价、库存、安全库存 | 库存是「当前值」不是「算出来的」 |
| 出入库流水 | 日期、商品、类型、数量、备注 | 每笔变动留痕，可追溯 |
| 订单表 | 客户、商品、数量、状态、日期 | 状态机：待处理 → 已发货 → 已完成 / 已取消 |

三张表用「商品」关联起来 —— **这就是关系型数据库最核心的一次连接**。

### 3. 定了一条关键业务规则
> **订单创建时不扣库存，点「发货」才扣；库存不够就拦住不让发。**

这条规则是我跟老板确认后定的。备选方案是「下单即扣」，但那样会出现「客人下单又不付款、货被锁死卖不出去」。**这是我第一次体会到：技术实现不难，难的是选哪个规则。**

### 4. 交付与迭代
【待填：你交付后对方说了什么、你改了哪一版】
> 例：老板第一反应是「太麻烦了，我还不如用本子」，因为他不想每次点三下才能记一笔。于是我加了「一键出库」的快捷入口……

## 五、面试官可能追问（提前想好）

1. **「这个系统跟买个现成的收银软件有什么区别？」**
   → 答：现成软件功能全但重，要培训、要收费、老板抗拒。我做的只解决他最痛的一件事，打开就会用。**先活下来再谈功能**。（诚实补一句：如果对方规模再大一点，我会推荐直接上现成 SaaS。）

2. **「为什么不用 Excel？」**
   → 答：Excel 能算但不会拦。我这条「库存不足不让发货」的规则 Excel 做不到。

3. **「这个 Demo 是你写的代码还是低代码搭的？」**
   → 诚实答：表结构和业务规则是我设计的，页面是我用原生 HTML/JS 实现的（为了能离线演示）；如果真上生产，我会用飞书多维表格搭，因为交付后客户自己能改。**这一问最忌讳含糊，一定要说清哪部分是你做的。**

4. **「如果客户不用了怎么办？」**
   → 答：先问为什么。多数情况不是不好用，是「多了一步」。把最常用的动作减到一步，比加十个功能有用。
