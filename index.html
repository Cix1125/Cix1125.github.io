案例 01 · 小微商户进销存系统（可交互 Demo）Case 01 · Inventory & Order System for a Micro Retailer

低代码 / 前端 · 独立完成 · 2026.09Low-code / Frontend · Solo · Sep 2026
问题

小店用本子记进货出货，月底靠计算器对账，经常漏单、账实不符；老板不知道「哪个货快没了」。 A small shop tracked stock in a paper notebook and reconciled monthly with a calculator — orders got missed and books never matched reality. The owner had no idea what was running out.

做法

先用一天蹲店画流程图，把「进 / 出 / 存 / 单」四件事拆成三张表（商品、流水、订单），做成一个打开就能用的单页系统：录入即更新库存、低库存自动预警、订单看板按状态拖动、一键导出对账表。 Spent a day in the shop mapping the flow, then split it into three entities (products, stock movements, orders) in a single-page tool: entries update stock instantly, low-stock alerts fire automatically, orders move across a kanban, reconciliation exports in one click.

结果

交付给我舅舅开的一家零售小店。他第一次看到时的原话是「太麻烦了，我还不如用本子」，所以我砍掉一半功能，把他每天重复最多的那个动作放到首页。这件事比代码本身更值得说。 Delivered to my uncle's retail shop. His first reaction was "too much hassle, I'd rather use the notebook", so I cut half the features and put the one action he repeats every day on the home screen. That lesson mattered more than the code.

案例 02 · 给 AI 装上「工作台」：可复用的交付环境Case 02 · Giving AI a Workbench: A Reusable Delivery Environment

AI 工作流 / 工程配置 · 独立完成 · 2026.09AI workflow / engineering setup · Solo · Sep 2026
问题

直接问 AI 干活有三个毛病：每次都要重复交代背景、同一件事两次结果不一样、改一点就要重来。 Using a chat AI for real work had three failure modes: re-explaining context every time, inconsistent output for the same request, and starting over for every tweak.

做法

部署本地 AI Harness（DeepSeek Harness）并把能力插件化：任务路由预设（按任务类型切换思考策略）、工具插件按需装载、热重载改配置不重启。把它固化成一套「开箱即用」的交付环境，而不是每次临时开个对话框。 Deployed a local AI harness and modularised its capabilities: a task-routing preset that switches reasoning strategy per task type, on-demand tool plugins, and hot reload so config changes need no restart — turning ad-hoc chat into a repeatable delivery environment.

结果

同类任务的重复交代成本降为 0——背景只讲一次，之后每次直接开工。 Re-briefing cost for repeat tasks fell to zero — brief once, then start work directly every time.

案例 03 · 英语 × AI：跨境内容交付工作流Case 03 · English × AI: A Cross-border Content Workflow

内容 / 本地化 · 进行中Content / Localisation · In progress
问题

出海卖家要同时产出中英双语商品文案、客服话术、平台政策摘要，量大且术语必须一致，人工做又慢又乱。 Cross-border sellers need Chinese and English product copy, support scripts and policy summaries at volume, with fully consistent terminology — slow and messy by hand.

案例 04 · crm-cleaner：客户主数据清洗与去重（开源）Case 04 · crm-cleaner: Customer Master Data Deduplication (Open Source)

数据工程 / 开源 · 已上线 · github.com/Cix1125/crm-cleanerData engineering / Open source · Shipped · github.com/Cix1125/crm-cleaner
问题

客户资料从多个系统导出，同一家公司写法不一样（「郑州云启科技有限公司」和「郑州云启科技」），各来源表的列名也不一致（手机 / 电话 / 联系方式）。人工合并只能靠眼看，还容易把两条不同客户的记录错并成一条。 Customer records exported from several systems spell the same company differently, and each source names its columns differently (mobile / phone / contact). Merging by hand means eyeballing thousands of rows — and wrongly merging two different customers.

做法

写了一个零第三方依赖的 Python 命令行工具：三层匹配（精确键 → 公司名规范化 → 相似度打分，阈值 0.88）；用 TOML 配置把各来源的列名映射到统一字段，这样换一家客户只改配置不改代码；输出主数据 + 重复组 HTML 报告 + 字段级变更日志——每一处取值都能追到来自哪个文件第几行。 Built a zero-dependency Python CLI: three-layer matching (exact key → normalised company name → similarity score, threshold 0.88); a TOML config maps each source's column names to shared fields, so onboarding a new client is a config change, not a code change; outputs master data + an HTML duplicate report + a field-level change log — every value traceable back to a source file and line.

结果

1195 行 Python（核心 855 + 测试 340）· 35 个测试全过 · CI 在 Python 3.11 / 3.12 / 3.13 上全绿 · MIT 协议 · 示例数据 10 条 → 识别 4 组重复 → 合并后 6 条。 1,195 lines of Python (855 core + 340 tests) · 35 tests passing · CI green on Python 3.11 / 3.12 / 3.13 · MIT licensed · sample data: 10 records → 4 duplicate groups → 6 after merge.
